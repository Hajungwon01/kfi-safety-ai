# 🧯 소방용품 안전지킴이 AI

> 소화기를 살 때부터 버릴 때까지, 챗봇 하나로 지켜주는 AI 서비스.
> KFI(한국소방산업기술원) 공공데이터로 소방기관 사칭 사기를 걸러내고, 내가 가진 소화기의 내용연수·리콜 여부를 계속 추적합니다.

2026년 KFI AI 혁신 경진대회 제출작 · FastAPI + 커스텀 HTML/CSS/JS

---

## 문제

**① 소방기관 사칭 사기**
최근 1년간 사칭 시도 **1,309건**, 실제 피해 업체 **161곳**, 누적 피해액 **약 29억 5천만원**(소방청 공식 발표). 소방서 간부를 사칭한 전화로 "리튬이온 소화기 없으면 과태료" 협박 → AI로 정교화된 위조 공문 발송 → 특정 업체 구매 강요/직접입금 유도 → 편취하는 수법이다. 전기차 화재 이슈로 리튬이온 대응용품 수요가 급증하면서 문제가 심화되는 중이고, 소방청도 "미인증 소화기 실태 일제 조사"에 착수했다.

**② 소방용품 생애주기 관리 공백**
분말소화기 내용연수는 10년(소방시설법 시행령), KFI 성능확인검사 합격 시 1회 3년 연장 가능하다. 하지만 리콜(승인취소) 정보가 개별 소유자에게 자동 전달되는 체계가 없다 — KFI 데이터포털에 공개는 되어 있지만 "내가 가진 제품이 리콜 대상인지" 확인할 방법이 일반인에게는 사실상 없다.

두 문제는 각각 **승인번호(모델 단위)**와 **합격표시번호(개별 유닛 단위)**라는 서로 다른 KFI 식별자를 쓴다는 공통점이 있다. 이 서비스는 이 둘을 구매 확인 → 내 소화기 관리로 잇는 하나의 흐름으로 통합했다.

| 승인번호 조회(취소/리콜) | "형식승인 제2019-3-102호 진짜예요?" |

상세 입력값은 `테스트_시나리오.md` 참고.

## 아키텍처

```
[브라우저]
  index.html(랜딩) → login.html(인증) → app.html(챗봇 단일 화면 + 프리셋 카드)
        │  Tesseract.js OCR(사진→텍스트, 클라이언트에서 처리)
        ▼
POST /api/chat  (FastAPI, JWT soft-auth)
        │
        ▼
chat_tools.detect_and_run(message)
   ├─ 정규식으로 의도 감지: 승인번호 / 업체명 / 합격표시번호 / 공문 텍스트 /
   │   "내 소화기함"·"내 알림" 명령형 / (미완성) 프리셋 placeholder
   │
   ├─ 감지됨 → 결정론적 서비스 로직 직접 호출 (사실 판정, LLM 관여 없음)
   │     kfi_client.get_approval / find_approval_loose
   │     kfi_client.find_company
   │     lifecycle(내용연수) + kfi_client.get_unit + find_recall_by_item_text
   │     doc_analyzer(공문 위험도 키워드 스코어링)
   │     notification_service / unit_service (내 소화기함, 알림)
   │
   └─ (OPENAI_API_KEY 있으면) 위 결과를 LLM에 주입해 자연어 설명만 생성
        없으면 rag.py 로컬 검색 결과를 그대로 반환 (LLM 실패해도 사실 조회 결과는 그대로 응답)
        │
        ▼
위험 판정(미등록/취소·리콜/고위험/안전등급 이상) → 응답에 args 포함
        → 프론트가 채팅 버블 안에 "🚨 신고하기" 인라인 버튼 렌더링 → POST /api/reports
```

**핵심 원칙**: 정품 여부·내용연수·리콜 여부 같은 "사실"은 항상 DB 대조로 결정하고, LLM은 그 결과를 설명하는 역할만 한다. 관제 대시보드(신고 통계, 리콜 트리거)는 `role=admin`에게만 열리며, 프론트 메뉴 숨김과 별개로 백엔드 API 레벨에서 403으로 강제한다.

## 기술 선택 이유

- **FastAPI(Python) + SQLite**: 이 프로젝트는 Node/Express판 → Streamlit판을 거쳐 지금 버전으로 두 번 재작성했다. Streamlit은 폼 기반 다중 페이지 앱을 만들기엔 편했지만, 채팅 UI를 중심에 두고 프리셋 카드·인라인 신고 버튼처럼 세밀한 DOM 조작이 필요해지면서 한계에 부딪혔다. 결국 백엔드는 가볍고 명시적인 FastAPI로, 프론트는 프레임워크 없이 직접 만든 HTML/CSS/JS로 정리했다. SQLite는 심사용 데모 규모에 별도 DB 서버가 필요 없다는 점 때문에 선택했다.
- **결정론적 로직과 LLM의 분리**: 화재안전 서비스에서 "이 소화기는 정품입니다"를 LLM이 확률적으로 판단하게 둘 수는 없다고 판단했다. 그래서 모든 사실 판정(`kfi_client`, `lifecycle`, `doc_analyzer`)은 순수 로직으로 먼저 실행하고, LLM은 그 결과를 문장으로 풀어 설명하는 역할만 맡긴다. `OPENAI_API_KEY`가 없거나 LLM 호출이 실패해도 이미 확정된 조회 결과는 그대로 응답된다.
- **로컬 TF-IDF 검색 + 임베딩 자동 업그레이드 (`rag.py`)**: 한국어 형태소 분석기를 따로 설치하지 않고도 동작해야 해서, 단어 대신 **문자 2-gram(bigram)** 단위로 토큰화한 뒤 TF-IDF 스코어링으로 검색하도록 만들었다. `OPENAI_API_KEY`가 있으면 임베딩 기반 코사인 유사도 검색으로 자동 전환되고, 임베딩 호출이 실패하면 다시 로컬 검색으로 폴백한다 — 두 경로 모두 항상 응답 가능해야 한다는 요구사항 때문.
- **Tesseract.js(브라우저 OCR)**: 공문·소화기 라벨 사진을 서버로 올려 OCR 서버를 따로 두는 대신, 브라우저에서 CDN으로 불러와 클라이언트에서 처리한다. 서버 인프라·비용 없이 사진 업로드 기능을 붙일 수 있어서 선택했다.

## 트러블슈팅 기록

### 1. KFI 승인/취소/업체 정보는 "단건조회"가 안 됨
- **문제 상황**: 채팅에 승인번호 하나를 입력하면 그 건만 바로 조회해서 보여주려 했는데, data.go.kr 상세 스펙을 보니 그런 API가 없었다.
- **원인 가설**: KFI가 공개한 승인정보·취소정보·업체정보 API는 날짜범위(`fromAprv~toAprv`)와 품목분류코드(`gdsClCd`) 기준의 "목록조회(페이징)"만 지원하고, 번호 하나로 찌르는 단건조회 파라미터 자체가 없다.
- **시도/검증**: data.go.kr 활용신청 승인 후 실제 요청 파라미터로 호출해보며 스펙을 재확인. 유일하게 정비이력(합격표시번호) API만 단건조회가 가능하다는 것을 발견.
- **해결**: 승인/취소/업체 정보는 관리자가 `POST /api/admin/sync-kfi`를 호출하면 목록을 전량 페이징해서 로컬 SQLite 캐시(`approval_cache`, `companies`)에 동기화하고, 사용자 조회는 항상 이 로컬 캐시를 보는 구조(`kfi_client.get_approval` 등)로 설계를 바꿨다. 정비이력만 실시간 단건조회를 그대로 사용.
- **결과**: 사용자 체감 응답속도는 유지하면서(캐시 조회라 즉시 응답) API 제약을 우회. 다만 동기화 주기에 따라 최신 데이터 반영에 지연이 생길 수 있다는 트레이드오프가 남음.

### 2. 승인번호를 채팅으로 입력하면 표기 차이로 조회가 안 됨
- **문제 상황**: mock 데이터의 승인번호와 정확히 똑같이 입력해야만 조회가 됐고, 공백이나 대소문자가 조금만 달라도 "미등록"으로 잘못 판정됐다.
- **원인 가설**: 채팅은 폼 입력과 달리 사용자가 자유 문장으로 타이핑하기 때문에 공백 유무, 대소문자, 숫자 `0`과 알파벳 `O`의 혼동이 흔하게 발생한다. 기존 `get_approval`은 정확 일치(`WHERE number=?`)만 봤다.
- **시도/검증**: 실제로 "제 0000-0-000호"처럼 공백을 넣거나 소문자로 입력하는 케이스를 재현해보니 전부 미등록으로 튕겼다.
- **해결**: 공백 제거·대문자 통일·`O→0` 치환을 하는 `_normalize()`를 추가하고, 정확 일치가 실패했을 때만 한 번 더 시도하는 `find_approval_loose()`를 별도로 만들어 `chat_tools.py`에서 폴백으로 호출하도록 함.
- **결과**: 표기가 조금 달라도 같은 번호로 인식. 폼 조회(`get_approval`)는 여전히 엄격한 정확 일치를 유지해 관리자 동기화 로직의 무결성은 그대로 보존.

### 3. 리콜(취소) 정보와 개별 소화기(합격표시번호)를 연결할 공식 필드가 없음
- **문제 상황**: "내 소화기함"에 등록된 개별 소화기가 나중에 리콜 대상이 됐을 때 이를 자동으로 알려주고 싶은데, 취소정보는 승인번호(모델) 단위이고 개별 유닛은 합격표시번호 단위라 조인할 키가 없었다.
- **원인 가설**: KFI 데이터 자체가 "모델 승인"과 "개별 유닛 정비이력"을 별도 체계로 관리하고 있어서, 애초에 두 단위를 공식적으로 잇는 필드가 존재하지 않는다.
- **시도/검증**: 실제 데이터 필드를 전수 비교해봤지만 공통 식별자를 찾지 못함. 대신 두 테이블 모두 제품명(품목명) 텍스트는 공통으로 가지고 있다는 점을 확인.
- **해결**: `find_recall_by_item_text()`로 취소된 승인 건의 품목명과 개별 유닛의 품목명을 부분 문자열 포함 관계로 근사매칭하도록 구현.
- **결과**: 리콜 알림 기능은 동작하지만 완벽한 매칭은 아니다 — 이 한계는 문서에 정직하게 남겨두고, 실서비스 전환 시 우선 보완 과제로 표시해뒀다.

### 4. 빈칸을 채우지 않은 프리셋 문구가 그대로 전송되면 LLM이 엉뚱한 답을 만듦
- **문제 상황**: 프리셋 카드를 눌러 채워진 예시 문구("합격표시번호 조회해줘")를 빈칸을 안 채우고 그대로 전송하면, `chat_tools.py`가 실제 번호를 못 찾아 도구 실행에 실패하고 일반 LLM 응답으로 넘어가면서 근거 없는 답이 나왔다.
- **원인 가설**: 도구 감지 정규식이 "실제 값이 있는 입력"만 노리고 만들어져 있어서, 빈칸이 그대로 남은 입력은 어떤 패턴에도 안 걸리고 곧장 RAG/LLM 폴백으로 빠졌다.
- **시도/검증**: 실제로 미편집 프리셋 문구를 그대로 보내보고 응답을 확인 — 예상대로 맥락 없는 일반 답변이 나왔다.
- **해결**: 프리셋 문구별 정확 일치 정규식(`PLACEHOLDER_HINTS`) 목록을 추가해, `detect_and_run()` 마지막 단계에서 LLM에 넘기기 직전에 가로채도록 함. 매칭되면 "실제 값으로 바꾸거나 📷로 사진을 올려달라"는 결정론적 안내를 반환한다. 진짜 FAQ성 질문("합격표시번호가 뭐예요?")은 이 정규식과 겹치지 않도록 좁게 설계해서 정상 동작은 그대로 유지.
- **결과**: 빈 값 입력이 더 이상 LLM 환각으로 이어지지 않음. 관련 시나리오는 `chat_widget_e2e.js`에 자동 테스트로 고정.

## 성과 지표

이 프로젝트는 아직 실제 서비스로 배포·운영된 적이 없어, 아래는 **구현 완성도/검증 지표**이며 실사용 성과가 아니다.

- 자동화 테스트 **152건 전부 통과**: pytest(순수 로직 + API 통합) 77건 + jsdom 프론트엔드 E2E 40건 + 챗봇 위젯 E2E 35건
- 검증 범위: 관리자 전용 API 접근 제어(403), 리콜 트리거 → 알림 반영, 프리셋 카드 빈칸 채우기 동작, 위험 결과의 채팅 내 인라인 신고 접수, 미편집 프리셋 문구의 placeholder 안내까지 실제 클릭·API 호출 재현
- KFI 실 API 연동: data.go.kr 활용신청 승인 및 서비스키 발급 완료, 실제 스펙 기준 구현 완료 (일부 하위 엔드포인트는 최초 실호출로 재검증 예정)
- 이 서비스가 대응하려는 문제 규모(참고): 최근 1년 소방기관 사칭 사기 시도 1,309건, 피해 업체 161곳, 피해액 약 29.5억원(소방청 발표)
